The XRP Ledger (XRPL) is a decentralized Layer 1 blockchain built for payments, with native support for issued currencies, a built-in decentralized exchange, automated market makers and NFTs.&#x20;

Validation Cloud serves the complete public ledger history, from ledger 32,570 to the current ledger, with WebSocket and HTTPS access.&#x20;

Developer docs: [https://xrpl.org/docs](https://xrpl.org/docs)

Mainnet block explorer: [https://livenet.xrpl.org](https://livenet.xrpl.org)

### Network Support

| Network      | Full History / Archive | HTTPS | WSS |
| ------------ | ---------------------- | ----- | --- |
| XRPL Mainnet | ✅                      | ✅     | ✅   |

> **Request format.** \
> \
> XRPL's HTTP API is JSON-RPC shaped but not JSON-RPC 2.0: the body is `{"method": "...", "params": [{...}]}` with no `jsonrpc` or `id` field. \
> \
> Over WebSocket, send `{"id": 1, "command": "...", ...}` with the parameters at the top level, as the xrpl.js and xrpl-py libraries do. \
> \
> The JSON-RPC shaped request `{"jsonrpc": "2.0", "id": 1, "method": "...", "params": [{...}]}` is accepted over WebSocket as well.

> **Validated by default.** Responses come from Clio, which serves validated ledger data. Requests that need the open ledger (`ledger_current`, `submit`, `fee`, or any request with `"ledger_index": "current"`) are forwarded to rippled automatically.

> **Errors are answers.** XRPL reports failures inside a `200 OK` response as `"status": "error"` with an `error` token (for example `lgrNotFound`, `actNotFound`), an `error_code` and an `error_message`. Check `result.status` rather than the HTTP status.

> **Not served.** `sign`, `sign_for` and `channel_authorize` take a secret key and are refused with `unknownCmd`; sign transactions client-side and send them with `submit`. `path_find` and the `peer_status`, `consensus` and `server` streams are not available.

> WebSocket clients **MUST** respond to server `ping` frames, otherwise the connection will be closed and re-established every minute.

### Endpoint Capabilities

XRPL endpoints support both HTTP and WebSocket connectivity for production-grade applications.

#### HTTP

Best suited for:

* backend services and APIs
* ledger and account data queries, including full history via `account_tx` and `ledger`
* transaction submission with `submit`
* development and testing workflows

#### WebSocket

Best suited for:

* the `ledger`, `transactions` and `validations` streams
* monitoring accounts and order books with `subscribe`
* xrpl.js and other WebSocket-first client libraries
* applications that require low-latency data delivery

### Getting Started

To start building on XRPL, connect your application to an XRPL endpoint and send XRPL API requests.

Example request over HTTPS:

<CodeGroup>

```bash title="mainnet"
curl https://mainnet.xrpl.validationcloud.io/v1/<YOUR_API_KEY_HERE> \
    -X POST \
    -H "Content-Type: application/json" \
    -d '{"method":"account_info","params":[{"account":"rMxCKbEDwqr76QuheSUMdEGf4B9xJ8m5De","ledger_index":"validated"}]}'
```

</CodeGroup>

Example request over WebSocket:

```bash
wscat -c wss://mainnet.xrpl.validationcloud.io/v1/<YOUR_API_KEY_HERE>
> {"id":1,"command":"account_info","account":"rMxCKbEDwqr76QuheSUMdEGf4B9xJ8m5De","ledger_index":"validated"}
```

With xrpl.js:

```javascript
import { Client } from "xrpl";

const client = new Client("wss://mainnet.xrpl.validationcloud.io/v1/<YOUR_API_KEY_HERE>");
await client.connect();
const info = await client.request({ command: "server_info" });
console.log(info.result.info.complete_ledgers);
await client.disconnect();
```
